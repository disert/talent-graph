# 智慧引才图谱 · 内网离线部署说明

面向运维：镜像与配置已打包好，服务器**不需要外网**、**不需要源码**。

---

## 一、交付物

| 文件 | 说明 |
| --- | --- |
| `talent-graph-images.tar` | 3 个镜像：`talent-graph-backend:latest`、`talent-graph-frontend:latest`、`pgvector/pgvector:pg16` |
| `docker-compose.yml` | 编排文件（与本文档同目录；服务器有 compose 插件时用） |
| `start-tg.sh` | 无 compose 环境的一键启动脚本：`bash start-tg.sh`（可重复执行） |
| `部署说明.md` | 本文档 |

> 后端镜像已内置 OCR：`paddlepaddle 3.3.1` + `paddleocr 3.7.0`，以及 3 个 OCR 模型
> （PP-OCRv6 检测/识别 + 文本行方向，约 145MB，位于镜像内 `/opt/paddlex_models`）。
> 因此后端镜像明显比之前大，导入会慢一些，属正常现象。

> 建议先用 sha256 校验 tar 包完整性（打包机与服务器两侧比对）：
> ```bash
> sha256sum talent-graph-images.tar
> ```

## 二、环境要求

- **架构**：Linux **x86_64**（镜像为 `linux/amd64`，ARM 服务器无法运行）
- **Docker**：20.10+，且带 `docker compose` v2 插件（`docker compose version` 能输出即可；
  注意是 `docker compose` 而不是老的 `docker-compose`）
- **磁盘**：≥ 15GB（后端镜像含 PaddleOCR 与 OCR 模型，约 2.8GB；`docker save` 的 tar 包另计，数据库与简历原件另计）
- **内存**：≥ 2GB
- **网络**：无需外网；但**服务器必须能访问配置里的大模型平台地址**（见第四节前置检查）
- **端口**：

| 端口 | 用途 | 是否需对外 |
| --- | --- | --- |
| 20022/tcp | 前端页面（nginx） | 需要，用户访问入口 |
| 20021/tcp | 后端 API + Swagger 文档 | 按需（仅本机排查可不开放） |
| 5432/tcp | PostgreSQL | 仅容器内部使用，非必要不对外开放 |

## 三、部署步骤

> **前置确认**：先跑 `docker compose version`。
> 若报 `docker: 'compose' is not a docker command`，说明服务器没装 compose 插件，
> **请直接跳到「附录 A」**，用 `docker run` 方式部署（或先离线安装 compose 插件）。

### 0. 确认环境

```bash
docker version
docker compose version
uname -m                 # 应输出 x86_64
```

### 1. 准备目录并上传文件

```bash
sudo mkdir -p /opt/talent-graph && cd /opt/talent-graph
# 将 talent-graph-images.tar 与 docker-compose.yml 上传到 /opt/talent-graph/
ls -l
```

### 2. 导入镜像

```bash
cd /opt/talent-graph
docker load -i talent-graph-images.tar
docker images | grep -E "talent-graph|pgvector"
```

应看到三行：`talent-graph-backend`、`talent-graph-frontend`、`pgvector/pgvector`。

### 3. 启动

```bash
docker compose up -d
```

> ⚠️ **绝对不要加 `--build`**。镜像已在本地，加 `--build` 会尝试重新构建，而服务器上没有源码、
> 也没有外网拉取基础镜像，必然失败。

### 4. 验收

```bash
docker compose ps                                  # db 应为 healthy，backend/frontend 为 Up
docker compose logs --tail=50 backend              # 看到 uvicorn 启动、建表日志

curl http://127.0.0.1:20021/api/health             # 期望 {"status":"ok"}
curl -I http://127.0.0.1:20022                     # 期望 HTTP/1.1 200 OK
curl http://127.0.0.1:20022/api/health             # 经 nginx 反代，同样返回 ok（证明前后端连通）
```

配置自检（推荐）：

```bash
docker compose exec backend python -c "from app.config import settings as s; print(s.llm_model, s.database_url)"
```

`database_url` 必须是 `postgresql+psycopg2://postgres:postgres@db:5432/talent_graph`。
若显示 `localhost`，说明 `docker-compose.yml` 里的 `environment` 没生效，后端连不上数据库。

**OCR 离线自检（强烈建议，验证扫描件简历可用）**：

```bash
docker exec talent-graph-backend python -c "import os,paddleocr,paddle;print('paddle',paddle.__version__,'paddleocr',paddleocr.__version__);print('cache',os.environ.get('PADDLE_PDX_CACHE_HOME'),'source',os.environ.get('PADDLE_PDX_MODEL_SOURCE'),'skip_check',os.environ.get('PADDLE_PDX_DISABLE_MODEL_SOURCE_CHECK'))"
```

然后真正跑一次识别（断网环境下应 15~60s 内出结果，**不应出现任何下载/超时**）：

```bash
docker exec talent-graph-backend python -c "import io;from PIL import Image,ImageDraw;from app.services.parser import _ocr_image_bytes;im=Image.new('RGB',(760,240),'white');ImageDraw.Draw(im).text((40,110),'Hello OCR 12345 Resume',fill='black');b=io.BytesIO();im.save(b,'PNG');print(repr(_ocr_image_bytes(b.getvalue())))"
```

预期输出类似 `'Hello OCR 12345 Resume'`（本地实测 14.45s / 首次含模型加载）。
若报模型缺失，说明用的是旧镜像或模型目录被覆盖，重新 `docker load` 最新镜像即可。

另外，日志里应该**只**出现这三个模型：`PP-LCNet_x1_0_textline_ori`、`PP-OCRv6_medium_det`、
`PP-OCRv6_medium_rec`。如果还看到 `UVDoc` 或 `PP-LCNet_x1_0_doc_ori`，说明容器里跑的不是新镜像。

### 5. 放行防火墙

```bash
# firewalld
sudo firewall-cmd --add-port=20022/tcp --permanent && sudo firewall-cmd --reload
# 或 ufw
sudo ufw allow 20022/tcp
```

如需给其他系统调 API，再放行 20021/tcp。

### 6. 访问

- 前端：`http://<服务器IP>:20022`
- API 文档：`http://<服务器IP>:20021/docs`

### 7. 如果服务器上已有旧版本

先检查一遍现状：

```bash
docker ps -a | grep talent-graph          # 是否已有同名容器
docker volume ls | grep talent-graph      # 是否有数据卷（有 = 以前部署过，历史数据在里面）
docker images | grep talent-graph         # 旧镜像
ss -lntp | grep -E '20021|20022|5432'     # 端口是否被占用
```

| 情况 | 要不要先删 |
| --- | --- |
| 全新服务器，上面都没有 | **不需要**，直接 `docker load` + `docker compose up -d` |
| 以前用本项目的 compose 部署过 | **不需要**，`docker load` 覆盖镜像后 `docker compose up -d --force-recreate backend frontend` |
| 以前用 `docker run` 起过同名容器（例如 `db`、`talent-graph-backend`） | **需要**，否则会报 `Conflict. The container name "/talent-graph-db" is already in use` 或端口冲突 → `docker rm -f <容器名>` |
| 数据卷 `talent-graph_pgdata` / `talent-graph_upload_data` | **绝不要删**，历史数据（岗位、简历、匹配结果、简历原件）都在卷里 |
| 旧镜像 | 不用手动删，`docker load` 会用同名标签直接覆盖；旧镜像变成 `<none>`，事后 `docker image prune` 可释放空间（不影响在用的容器） |

> - 覆盖升级前建议先备份（见「备份 / 恢复」）。
> - 只有确认「数据不要了」时才用 `docker compose down -v`——它会连数据卷一起删。

## 四、前置检查：大模型平台连通性

后端所有「简历解析 / 岗位结构化 / 匹配精排」都依赖内网大模型平台。**宿主机通不代表容器通**，
建议按下面这条命令在容器里实测（把 IP/端口换成实际平台地址）：

```bash
docker compose exec backend python -c "import socket; socket.create_connection(('10.137.64.110', 8001), 5); print('PLATFORM REACHABLE')"
```

- 打印 `PLATFORM REACHABLE` → 网络通，可以开始使用；
- 报 `timed out` / `Network is unreachable` → 服务器到平台的网络/防火墙未放通，需先解决，
  否则上传简历会一直停在「解析失败」。

## 五、常见问题

| 报错 / 现象 | 原因与处理 |
| --- | --- |
| `Bind for 0.0.0.0:5432 failed: port is already allocated` | 宿主机已有 PostgreSQL 占用 5432。停掉旧服务，或把 `docker-compose.yml` 中 db 的 `ports` 改为 `"15432:5432"`（后端走容器网络，不受影响） |
| `failed to read dockerfile: ... Dockerfile: no such file` | 镜像没导入成功就触发了构建。确认 `docker images` 里有这两个镜像后再 `up` |
| `Bind for 0.0.0.0:20021/20022 failed` | 端口被占用：`ss -lntp \| grep -E '20021\|20022'` |
| `pull access denied` / `no matching manifest` | 服务器无外网却尝试拉镜像，通常是因为误加了 `--build`，或镜像名不一致 |
| db 长时间 `unhealthy` | `docker compose logs db` 查看；若数据卷来自旧环境且口令被改过，会出现连不上 |
| `[TERM] No valid user for confirmation. Please contact the administrator.` | **这不是 Docker 的报错**，是主机安全管控组件（等保加固 / 国产 OS 强制访问控制 / 终端安全软件）拦截了命令，最容易被拦的是 `docker run` 里的 `-p`（在宿主机开启监听端口）。① 先改用脚本执行 `bash start-tg.sh`（脚本内的命令通常不经过交互式 shell 的管控 hook）；② `type docker` 看是否被别名/函数包装，改用 `command docker ...` 或 `/usr/bin/docker ...`；③ 用 `/usr/bin/docker run -d --name t1 -p 20033:80 talent-graph-frontend:latest` 单测「发布端口」是否被拦；④ 仍不行需联系管理员在管控策略中放行 docker |
| 前端 502 Bad Gateway | 后端未就绪：`docker compose logs backend` |
| 页面能打开但接口 500 | 多为大模型平台不可达或地址错误，看后端日志里的具体异常 |
| 组织架构里混着「集团总部 / 省级电力公司 / 科研院所与设计单位 / 产业与新兴业务公司」这些示例部门 | 首次建库时播种的内置示例树，可整棵清掉：见「附录 C」 |
| 上传简历后一直「解析失败」 | 先查第四节平台连通性（PDF/Word 也会失败）；若只有**扫描件/图片**失败，看日志里 `OCR 引擎初始化失败 / 文字识别失败` 的具体原因（多为模型缓存缺失或系统库缺失），并用第四节的「OCR 离线自检」验证 |
| 日志里出现 `huggingface.co` / 下载模型 | 镜像已烘入 OCR 模型，并设了 `PADDLE_PDX_MODEL_SOURCE=bos` + `PADDLE_PDX_DISABLE_MODEL_SOURCE_CHECK=True`（见 `backend/Dockerfile`）。若仍出现，说明容器跑的不是本项目镜像，或启动时人为覆盖了这些环境变量（`docker inspect <容器> \| grep -i paddle` 可查） |
| 想改配置（模型地址/密钥/端口） | 配置烘入镜像，改 `backend/.env` 后必须 `docker compose build backend && docker compose up -d --force-recreate backend`（`DATABASE_URL` 例外） |

### 备份 / 恢复

```bash
mkdir -p /opt/backup

# 数据库
docker compose exec -T db pg_dump -U postgres talent_graph > /opt/backup/tg_$(date +%F).sql

# 简历原件（命名卷 talent-graph_upload_data）
docker run --rm -v talent-graph_upload_data:/data -v /opt/backup:/backup \
  alpine tar czf /backup/uploads_$(date +%F).tar.gz -C /data .
```

恢复数据库：

```bash
docker compose exec -T db psql -U postgres talent_graph < /opt/backup/tg_2026-09-15.sql
```

> 数据卷名来自 compose 项目名（目录名 `talent-graph`）：`talent-graph_pgdata`、`talent-graph_upload_data`。
> **数据库与原件要一起备份**，否则导出 ZIP 时简历会标「（原件缺失）」。

### 修改配置

后端配置（大模型平台地址、密钥、匹配参数）已烘焙进镜像，服务器上**没有 `.env` 文件**。
要修改必须重新出镜像：在打包机改 `backend/.env` → `docker compose build backend` →
重新 `docker save` 发过来 → `docker load` + `docker compose up -d --force-recreate backend`。

> 唯一例外：数据库连接串 `DATABASE_URL` 由 `docker-compose.yml` 的 `environment` 在运行时注入，
> 改它只需 `docker compose up -d --force-recreate backend`。

## 七、安全提醒

- 镜像内**含大模型平台 API Key（明文）**，tar 包与镜像请走安全通道传输，不要外发或推到不可信仓库。
- 数据库默认口令为 `postgres/postgres`，后端 API 当前**无鉴权**，请勿把 20021 直接暴露到公网。
- 若要改数据库口令：`docker-compose.yml` 里的 `POSTGRES_PASSWORD` 与 `DATABASE_URL` 需同步修改，
  且**数据卷已存在时改 `POSTGRES_PASSWORD` 不会更新库内已有口令**，需额外执行一次：
  ```bash
  docker compose exec db psql -U postgres -c "ALTER USER postgres WITH PASSWORD '新口令';"
  ```

## 附录 A：服务器上没有 `docker compose` 插件

两种办法，任选其一。**推荐 A-2**（装上插件后，前面所有步骤与命令都不用改）。

### A-1. 完全不用 compose，改用 `docker run`

效果与 compose 完全等价。**必须按顺序执行**，其中 `--network-alias backend` 是关键：
前端 nginx 的配置是 `proxy_pass http://backend:8000`，靠这个别名才能找到后端。

> 说明：若执行 `docker run -p ...` 时报 `[TERM] No valid user for confirmation. Please contact
> the administrator.`，那是主机安全管控组件的拦截（不是 Docker 报错），处理办法见「五、常见问题」。
> 也可先直接试 `bash start-tg.sh`。

**① 建专用网络**

```bash
docker network create talent-graph
```

**② 数据库**

```bash
docker run -d --name talent-graph-db --network talent-graph --restart unless-stopped -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=talent_graph -v talent-graph_pgdata:/var/lib/postgresql/data pgvector/pgvector:pg16
```

**③ 等数据库就绪**（否则后端启动会失败）

```bash
until docker exec talent-graph-db pg_isready -U postgres >/dev/null 2>&1; do sleep 2; done
```

**④ 后端**（`--network-alias backend` 不能省，否则前端 502）

```bash
docker run -d --name talent-graph-backend --network talent-graph --network-alias backend --restart unless-stopped -p 20021:8000 -e DATABASE_URL=postgresql+psycopg2://postgres:postgres@talent-graph-db:5432/talent_graph -v talent-graph_upload_data:/app/data/uploads talent-graph-backend:latest
```

**⑤ 前端**（必须在后端之后启动：nginx 启动时就要解析 `backend` 主机名）

```bash
docker run -d --name talent-graph-frontend --network talent-graph --restart unless-stopped -p 20022:80 talent-graph-frontend:latest
```

**更省事的办法**：直接用随包提供的 `start-tg.sh`（把上述 5 步串起来，可重复执行）：

```bash
bash start-tg.sh
```

> 若某条命令仍被拦截，先 `type docker` / `alias | grep docker` 确认是否被别名或函数包装
> （用 `/usr/bin/docker` 绝对路径可绕过），或联系管理员申请 `docker run` 权限。
> 若脚本报 `$'\r': command not found`，说明文件是 Windows 换行，先执行 `sed -i 's/\r$//' start-tg.sh`。

验收命令与前面一致，只是把 `docker compose exec` 换成 `docker exec`：

```bash
docker ps                                                       # 3 个容器均为 Up
docker logs --tail=50 talent-graph-backend
curl http://127.0.0.1:20021/api/health                          # {"status":"ok"}
curl -I http://127.0.0.1:20022                                  # 200 OK
docker exec talent-graph-backend python -c "from app.config import settings as s; print(s.llm_model, s.database_url)"
```

**命令对照表**（无 compose 时日常运维用）：

| compose 命令 | 等效 docker 命令 |
| --- | --- |
| `docker compose ps` | `docker ps` |
| `docker compose logs -f backend` | `docker logs -f talent-graph-backend` |
| `docker compose restart backend` | `docker restart talent-graph-backend` |
| `docker compose stop` | `docker stop talent-graph-frontend talent-graph-backend talent-graph-db` |
| `docker compose start` | `docker start talent-graph-db talent-graph-backend talent-graph-frontend` |
| `docker compose exec backend ...` | `docker exec talent-graph-backend ...` |
| `docker compose down`（保留数据） | `docker rm -f talent-graph-frontend talent-graph-backend talent-graph-db` |
| `docker compose down -v`（**删数据**） | 上面那条 + `docker volume rm talent-graph_pgdata talent-graph_upload_data` |

### A-2. 离线安装 compose 插件（推荐）

compose v2 是一个**静态二进制**，不需要联网安装，也不依赖 Python。在打包机（有外网）下载后拷过去即可：

```bash
# 打包机：下载 Linux x86_64 版（约 60MB）
curl -L -o docker-compose https://github.com/docker/compose/releases/latest/download/docker-compose-linux-x86_64

# 服务器：放到 CLI 插件目录并赋可执行权限
sudo mkdir -p /usr/local/lib/docker/cli-plugins
sudo cp docker-compose /usr/local/lib/docker/cli-plugins/docker-compose
sudo chmod +x /usr/local/lib/docker/cli-plugins/docker-compose

# 验证
docker compose version
```

## 附录 B：通过反向代理挂在二级路径下访问

**场景**：应用装在一台机器上（例 A 机 `10.137.44.149`，监听 20021/20022），
内网电脑**不能直连 A 机**，只能在另一台机器（例 B 机 `10.137.74.32`）上用 nginx 转发，
而且要挂在二级路径 `/talent-graph/...` 下，免得和 B 机上其它业务抢根路径。

### B-0. 现象与原因

**现象**：浏览器打开后页面能加载，但**内容空白**（`F12` 看 `<div id="root">` 是空的）。

**原因**：前端默认按**绝对路径**打包 —— index.html 里引的是 `/assets/index-xxxx.js`。
经 B 机访问时浏览器会去请求 `http://B机/assets/index-xxxx.js`，B 机上没有这个 location，
返回 404 → JS 根本没加载 → React 没机会渲染，`#root` 就是空的。接口同理（默认打 `/api/...`）。

所以在 B 机上改 nginx 没用，**要让前端按二级路径重新打包**。

### B-1. 在打包机重出前端镜像

```bash
cd talent-graph
docker compose build frontend        # 两个 args 已写在 docker-compose.yml 里

# 不用 compose 时等价于：
docker build -t talent-graph-frontend:latest --build-arg VITE_BASE_PATH=/talent-graph/frontend/ --build-arg VITE_API_BASE=/talent-graph/backend/api ./frontend
```

| 参数 | 作用 |
| --- | --- |
| `VITE_BASE_PATH` | 静态资源前缀 `/talent-graph/frontend/`，改掉后资源请求才会带上二级路径 |
| `VITE_API_BASE` | 接口前缀 `/talent-graph/backend/api`；模板下载、结果导出这些链接也跟着变 |

> 前端容器内的 nginx 会主动剥掉 `/talent-graph/frontend/`、`/talent-graph/backend/` 前缀，
> 所以这份镜像**直连 A 机 20022 也照用**（根路径与带前缀的地址都可以）。

### B-2. B 机（74.32）上的 nginx 配置

```nginx
# 前端页面
location /talent-graph/frontend {
    proxy_pass http://10.137.44.149:20022;      # ★ 结尾不要加斜杠
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 600s;
    proxy_send_timeout 600s;
}

# 后端接口（前端所有请求都走这里）
location /talent-graph/backend {
    proxy_pass http://10.137.44.149:20021;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 600s;
    proxy_send_timeout 600s;
    client_max_body_size 100m;      # ★ 上传简历/Excel 必需，nginx 默认 1m 会直接 413
}
```

**两个坑**：

1. `proxy_pass` **结尾不要加斜杠**（`http://...:20022;` 而不是 `http://...:20022/;`）。
   加了斜杠会把 `/talent-graph/frontend` 前缀直接砍掉，容器内 nginx 反而匹配不到；
   原样透传、由容器内 nginx 统一剥前缀，直连与二级路径两种访问才能同时成立。
2. `client_max_body_size 100m;` 必须加在**后端**那个 location 上。
   默认只允许 1MB 请求体，上传简历 / Excel 会直接 413，而后端日志里什么都看不到。

### B-3. 验收

```bash
curl -sI http://10.137.74.32/talent-graph/frontend/                   # 期望 HTTP 200 + text/html
curl -sI http://10.137.74.32/talent-graph/frontend/assets/ | head -1  # 期望 404/403（目录），不是 502
curl -s  http://10.137.74.32/talent-graph/backend/api/health          # 期望 {"status":"ok"}
```

浏览器打开 `http://10.137.74.32/talent-graph/frontend/`，按 `F12 → 网络`：

- JS / CSS 请求路径应该是 `/talent-graph/frontend/assets/...` 且**全部 200**；
- 若看到 `/assets/...` 这样的请求打到了 404，说明浏览器拿到的还是旧镜像（没带构建参数）——
  重新 `docker load` 新前端镜像并 `docker rm -f talent-graph-frontend` 后重启即可（浏览器强制刷新）。
- 页面左侧出现 5 个菜单就说明 React 已正常挂载。

## 附录 C：清掉内置示例组织架构

首次建库（`departments` 表为空）时后端会播种一份内置示例树，方便空库就能选部门：

```
集团总部 ／ 省级电力公司 ／ 科研院所与设计单位 ／ 产业与新兴业务公司
```

有真实数据后它只会碍事，可以整棵删掉（**只删这 4 棵示例子树，自己导入的一律保留**）。

**会不会自己长回来？** 不会。播种规则是「表为空才播种」，删完后表里还有你的真实部门，
重启后端不会重新播种。⚠️ 唯一会把它加回来的是界面上的「恢复默认」按钮，别点。

**执行**（脚本为 `cleanup-demo-departments.sql`，与本文档同级目录）：

```bash
cd /opt/talent-graph

# compose 部署
docker compose exec -T db psql -U postgres -d talent_graph -v ON_ERROR_STOP=1 < cleanup-demo-departments.sql

# docker run 部署（容器名 talent-graph-db）
docker exec -i talent-graph-db psql -U postgres -d talent_graph -v ON_ERROR_STOP=1 < cleanup-demo-departments.sql
```

脚本做三件事：

1. 列出将删除的节点（执行前请核对）；
2. 逐个核对子树里的**完整路径**是否都在内置示例清单里，一旦发现混进来的节点
   （比如你在示例根下面挂了真实部门）→ **整单中止、什么都不删**；
3. 删除并打印剩余的根节点与总数。

**先看后删**：把脚本最后的 `COMMIT;` 改成 `ROLLBACK;` 再跑一遍即可，其它不用改。

**两点说明**：

- `departments.parent_id` 是 `ON DELETE CASCADE`，删根节点会连子树一起删（内置示例共 34 个节点）。
- 岗位的省份是**建岗时就写进** `job_requests.province` 的，删部门不会改掉它；
  但若真有岗位挂在示例部门下，它们在匹配页的级联里会落到自动补建的路径下。
  脚本会额外列出「引用了示例部门的岗位」，建议先把这些岗位改挂到真实部门再删。

（只给当前用户装的话，放 `~/.docker/cli-plugins/docker-compose` 同样有效。
文件名必须是 `docker-compose`，带连字符，才能以 `docker compose` 子命令形式调用。）

装好后，前面「三、部署步骤」可以直接照做。

### 注意事项

- 用 A-1 方式建的**数据卷名与 compose 完全一致**（`talent-graph_pgdata`、`talent-graph_upload_data`），
  两种方式可以互相切换、数据通用；但**容器名相同**，切换前需先 `docker rm -f` 掉原有三个容器（卷不要删）。

## 附录 B：目标服务器不能被直接访问时，在前面加一层代理

典型拓扑（回显机器两边都通）：

```
用户浏览器 ──► [代理服务器 nginx :80/443] ──► 目标服务器 :20022（前端页面）
                                          └─► 目标服务器 :20021（API 文档，可选）
```

### B-1. 推荐：nginx 反向代理（HTTP 层）

在代理服务器上加一个 server 块：

```nginx
server {
    listen 80;                       # 或 8080 / 443 ssl
    server_name talent.example.local;

    client_max_body_size 100m;       # 必须放开，否则批量上传简历报 413
    proxy_read_timeout 300s;
    proxy_send_timeout 300s;

    location / {
        proxy_pass http://<目标服务器IP>:20022;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_buffering off;         # 导出 ZIP 是流式下载，关掉缓冲更稳
    }
}
```

**只需要代理 20022 这一个端口。** 前端页面里的接口地址是相对路径 `/api`，请求发到前端容器的 nginx
后再由它转发给后端容器，所以代理层不必单独处理 20021。

如果还要让其他系统直接调 API 或看 Swagger 文档，再加一个：

```nginx
server {
    listen 20021;
    server_name _;
    client_max_body_size 100m;
    location / {
        proxy_pass http://<目标服务器IP>:20021;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

### B-2. 其他等效做法

| 场景 | 做法 |
| --- | --- |
| Linux，只想做 TCP 端口转发 | `iptables -t nat -A PREROUTING -p tcp --dport 20022 -j DNAT --to-destination <目标IP>:20022`（需 `sysctl -w net.ipv4.ip_forward=1`，并放行 FORWARD 链） |
| 代理服务器是 Windows | `netsh interface portproxy add v4tov4 listenport=20022 listenaddress=0.0.0.0 connectport=20022 connectaddress=<目标IP>` |
| 只是自己临时调试 | `ssh -L 20022:<目标IP>:20022 user@代理服务器`，然后浏览器访问 `http://127.0.0.1:20022` |
| 需要域名 / HTTPS | 在反代层配证书（`listen 443 ssl;`），对外统一用 `https://talent.xxx.local` |

### B-3. 三个最容易踩的坑

1. **上传简历报 413 Request Entity Too Large** → 代理层（以及再上一层的负载均衡/网关）`client_max_body_size` 没放开。
2. **打开页面很慢或 504** → `proxy_read_timeout` 太短。简历解析、匹配精排都要走大模型，耗时可能上百秒。
3. **只代理了 `/api` 没代理 `/`** → 页面白屏。前端是 SPA，`/` 和 `/api` 必须一起代理（用 B-1 的单个 `location /` 即可全覆盖）。
4. **挂在子路径下（如 `http://proxy/talent/`）会白屏**。前端构建时资源用的是绝对路径 `/assets/...`，
   除非改 `vite.config.ts` 的 `base` 并重新构建镜像。**请用独立端口或独立域名**，不要挂子路径。

### B-4. 验证

在代理服务器上执行：

```bash
curl -I http://<目标服务器IP>:20022          # 应先确认代理机能通目标机
curl -I http://127.0.0.1:20022               # 再确认代理配置生效（换成代理监听端口）
curl http://127.0.0.1:20022/api/health       # 期望 {"status":"ok"}
```
